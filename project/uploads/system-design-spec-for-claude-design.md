# System Design Spec: ระบบจัดการเว็บโฮสติ้งสำหรับนักศึกษา (Student Shared Hosting Platform)

> เอกสารนี้จัดทำขึ้นเพื่อส่งต่อให้ **Claude Design** ใช้ออกแบบหน้าตา (UI/UX) และผังระบบต่อจากแนวคิดทางเทคนิคที่ผ่านการวิเคราะห์แล้วในรายงานฉบับหลัก (LAMP Stack บน TurnKey GNU/Linux)

---

## 1. ภาพรวมผลิตภัณฑ์ (Product Overview)

**ชื่อระบบ (ชั่วคราว):** Student Hosting Portal

**เป้าหมาย:** เว็บพอร์ทัลที่ให้นักศึกษาสมัครขอพื้นที่เว็บโฮสติ้งด้วยตนเอง (self-service) บนเซิร์ฟเวอร์ TurnKey LAMP ของสถาบัน โดยระบบเบื้องหลังจะสร้างบัญชีผู้ใช้ Linux, โควตาพื้นที่, ฐานข้อมูล MariaDB และ URL เว็บไซต์ให้อัตโนมัติ

**ผู้ใช้งานหลัก (User roles):**

| บทบาท | ความต้องการหลัก |
|---|---|
| นักศึกษา (Student) | สมัครใช้งาน, ดูสถานะโควตา, ดาวน์โหลดข้อมูลเชื่อมต่อ SSH/SFTP และฐานข้อมูล, รีเซ็ตรหัสผ่าน |
| เจ้าหน้าที่/อาจารย์ผู้ดูแลระบบ (Admin) | อนุมัติ/ระงับบัญชี, ดูภาพรวมการใช้ทรัพยากรทั้งระบบ, ปรับโควตารายบุคคล, ลบบัญชีที่ไม่ใช้งาน |

---

## 2. Key User Flows

### 2.1 Flow: นักศึกษาสมัครใช้งาน (Self-Service Signup)
1. นักศึกษาเข้าหน้าเว็บ → กรอกแบบฟอร์ม (ชื่อ-นามสกุล, รหัสนักศึกษา, อีเมลสถาบัน, username ที่ต้องการ)
2. ระบบตรวจสอบ username ซ้ำ/รูปแบบถูกต้อง (a-z0-9 เท่านั้น, 4–16 ตัวอักษร)
3. ระบบส่ง OTP/ลิงก์ยืนยันไปยังอีเมลสถาบัน
4. ยืนยันตัวตนสำเร็จ → ระบบเรียก Provisioning Script สร้างบัญชีจริงบนเซิร์ฟเวอร์
5. แสดงหน้า "สมัครสำเร็จ" พร้อมสรุปข้อมูลเชื่อมต่อ (ดาวน์โหลดเป็นไฟล์หรือคัดลอก)

### 2.2 Flow: นักศึกษาเข้าดูแดชบอร์ดของตนเอง
1. ล็อกอินด้วย username/รหัสผ่าน (หรือ SSO ของสถาบัน)
2. เห็นสรุป: โควตาที่ใช้ไป/ทั้งหมด (progress bar), Base URL ของเว็บไซต์ตนเอง, สถานะฐานข้อมูล
3. ปุ่มลัด: เปลี่ยนรหัสผ่าน SSH/SFTP, เปลี่ยนรหัสผ่านฐานข้อมูล, ดาวน์โหลดคู่มือเชื่อมต่อ FileZilla

### 2.3 Flow: เจ้าหน้าที่ดูแลระบบ (Admin Panel)
1. ล็อกอินด้วยสิทธิ์ผู้ดูแล
2. เห็นตารางผู้ใช้ทั้งหมด: username, การใช้พื้นที่, วันที่สมัคร, สถานะ (ปกติ/ระงับ/เกินโควตา)
3. ค้นหา/กรองผู้ใช้ตามรายวิชาหรือปีการศึกษา
4. Action ต่อผู้ใช้: ปรับโควตา, ระงับบัญชีชั่วคราว, ลบบัญชีถาวร (พร้อม confirm dialog)
5. แดชบอร์ดภาพรวมทรัพยากรระบบ: กราฟการใช้ดิสก์รวม, จำนวนผู้ใช้ทั้งหมด vs. จำนวนสูงสุดที่รองรับ (อ้างอิงจากไฟล์คำนวณ capacity planning)

## 3. หน้าจอที่ต้องออกแบบ (Screens Needed)

| หน้าจอ | องค์ประกอบสำคัญ |
|---|---|
| หน้าแรก/แนะนำบริการ | โลโก้สถาบัน, คำอธิบายบริการสั้น ๆ, ปุ่ม "สมัครใช้งาน" และ "เข้าสู่ระบบ" |
| ฟอร์มสมัครสมาชิก | ช่องกรอกข้อมูล, ตัวช่วยตรวจสอบ username แบบ real-time, ข้อตกลงการใช้งาน (Terms) |
| หน้ายืนยันอีเมล/OTP | ช่องกรอกรหัส 6 หลัก, ปุ่มส่งรหัสใหม่ |
| หน้าสมัครสำเร็จ | สรุปข้อมูล: Base URL, วิธีเชื่อมต่อ SSH/SFTP, ข้อมูลฐานข้อมูล, ปุ่มดาวน์โหลด PDF/Text |
| แดชบอร์ดนักศึกษา | การ์ดสรุปโควตา (progress bar), การ์ดสถานะเว็บไซต์/ฐานข้อมูล, เมนูตั้งค่าบัญชี |
| แผงควบคุมผู้ดูแลระบบ | ตารางผู้ใช้ (sortable/filterable), การ์ดสรุปทรัพยากรรวม, หน้าจัดการรายผู้ใช้ |
| หน้าตั้งค่าบัญชี | เปลี่ยนรหัสผ่าน SSH/SFTP, เปลี่ยนรหัสผ่านฐานข้อมูล, ปิด/ลบบัญชีของตนเอง |

## 4. โมเดลข้อมูลเชิงแนวคิด (Conceptual Data Model)

```
User
├─ student_id (รหัสนักศึกษา)
├─ full_name
├─ email (สถาบัน)
├─ username        # ตรงกับ Linux user, MariaDB user, MariaDB database, subdomain
├─ status          # pending | active | suspended | deleted
├─ quota_soft_mb
├─ quota_hard_mb
├─ disk_used_mb    # sync จากเซิร์ฟเวอร์เป็นระยะ
├─ base_url         # username.hosting.college.ac.th
├─ created_at
└─ role            # student | admin
```

**หมายเหตุสำคัญ:** `username` เป็นคีย์ร่วมที่ผูกกับทุกทรัพยากร (บัญชี Linux, ฐานข้อมูล MariaDB, ผู้ใช้ฐานข้อมูล, Virtual Host/Subdomain) — การออกแบบ UI ควรเน้นให้ username เป็นสิ่งที่ผู้ใช้เปลี่ยนไม่ได้หลังยืนยันตัวตนแล้ว

## 5. ข้อจำกัดทางเทคนิคที่มีผลต่อการออกแบบ UI

- ระบบเบื้องหลังทำงานผ่านสคริปต์บนเซิร์ฟเวอร์ TurnKey Linux (ไม่ใช่ระบบคลาวด์ API แบบพร้อมใช้) → การกระทำที่กระทบเซิร์ฟเวอร์จริง (สร้าง/ลบบัญชี) ควรมีการยืนยันซ้ำ (confirm modal) เสมอ
- การใช้พื้นที่ดิสก์ (`disk_used_mb`) อัปเดตแบบไม่เรียลไทม์ (sync เป็นรอบ เช่น ทุก 15 นาที) → UI ควรแสดง "อัปเดตล่าสุดเมื่อ..." กำกับตัวเลขโควตาเสมอ
- ผู้ใช้เชื่อมต่อไฟล์ผ่าน FileZilla (SFTP) ไม่ใช่ผ่านหน้าเว็บ → แดชบอร์ดไม่จำเป็นต้องมี File Manager ในเวอร์ชันแรก เพียงแสดงข้อมูลเชื่อมต่อให้ครบถ้วน
- จำนวนผู้ใช้สูงสุดที่ระบบรองรับถูกจำกัดด้วยสเปกเซิร์ฟเวอร์ (ดูไฟล์ Excel คำนวณโควตา) → ควรมี state "เต็มโควตา ไม่รับสมัครเพิ่ม" ในฟอร์มสมัคร

---

## 6. โทนการออกแบบที่แนะนำ (Design Direction)

- ภาษาในอินเทอร์เฟซ: ภาษาไทยเป็นหลัก (ศัพท์เทคนิคภาษาอังกฤษกำกับในวงเล็บได้ เช่น "โควตา (Quota)")
- กลุ่มผู้ใช้เป็นนักศึกษาอาชีวศึกษา → เน้นความเรียบง่าย ขั้นตอนน้อย ไอคอนสื่อความหมายชัดเจน
- ใช้สีสถาบันการศึกษาเป็นสีหลัก (ให้ผู้ใช้ระบุหรือปรับภายหลัง) และใช้สีสถานะมาตรฐาน (เขียว = ปกติ, เหลือง = ใกล้เต็มโควตา, แดง = เกินโควตา/ถูกระงับ)

---

## 7. สิ่งที่ยังไม่รวมในเวอร์ชันนี้ (Out of Scope)

- File Manager แบบเว็บ (ผู้ใช้จัดการไฟล์ผ่าน FileZilla เท่านั้น)
- ระบบชำระเงิน/แพ็กเกจแบบมีค่าใช้จ่าย
- การรองรับหลายเซิร์ฟเวอร์ (Multi-server / Load Balancing)
